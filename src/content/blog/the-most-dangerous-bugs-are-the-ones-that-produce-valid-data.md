Some bugs crash applications. Some produce incorrect results. And then there are bugs that produce perfectly valid results, even though the underlying logic is wrong.

I've encountered quite a few bugs during my career. Some were configuration issues, while others were simply incorrect implementations. But this story is a little different. It wasn't a straightforward case where someone reported a malfunction and we investigated its root cause. In fact, this bug might have gone unnoticed for much longer if we hadn't stumbled upon it while working on something completely unrelated.

## The Anomaly in the Billing Logic

We have a checkout and billing page where all the calculations happen on the frontend. The calculated values are displayed to the user and then sent to the backend for validation and storage.

Everything had been working fine for months. There were no reported issues, and nothing suggested that something was wrong—until we started working on a new feature.

We needed to implement the same calculation logic for another flow, and the billing process had to behave exactly as it did in the existing checkout flow. So I thought, why replicate the same logic when we could extract the existing calculation into reusable parts? It would also make the implementation easier to maintain.

I started going through the existing implementation and noticed a line that had been there for quite some time:

```javascript
const netAmount = totalAmount - discount;
```

Something felt strange.

According to the billing logic, the amounts of all items should be added first, then the discount should be deducted, followed by the tax calculation. Seeing the backend subtract the discount like this made me pause. If the frontend was already calculating and sending the final figures, why was the backend deducting the discount a second time?

What puzzled me even more was that this value matched the amount generated by the backend calculation. The issue had never been reported, there were no visible consequences, and the billing process appeared to be working as expected. I tested the implementation myself, but everything seemed normal.

Why was this working?

## Down the Git Rabbit Hole

I started investigating when this change was introduced, hoping the commit history would give me some clues. And that's when I found something I wasn't expecting.

It turned out that this subtraction had been introduced as a fix for an issue shortly after the initial release. But why was it needed in the first place?

I suspected something might be happening on the frontend, so I opened the frontend repository and traced the API call. Before sending the request, the request body was being constructed, and I found something interesting: the frontend was actually *adding* the discount to the total amount.

It was a typo that had somehow survived all this time.

## Two Wrongs Making a "Right"

So the two implementations were compensating for each other's mistakes:

- The frontend was adding the discount to the total amount.
- The backend was subtracting the discount from the received amount.

For example, if the item total was ₹1,000 and the discount was ₹100:

```javascript
// Frontend (incorrect)
const totalAmount = 1000 + 100; // 1100

// Backend (incorrect compensation)
const netAmount = 1100 - 100; // 1000
```

The final result matched the expected amount, so nothing appeared to be broken.

Looking back, the backend change was probably introduced to make the implementation work without investigating why the frontend was sending an unexpected amount in the first place. And since it fixed the immediate problem, it stayed.

## The Real Danger of Silent Bugs

I discovered this almost by accident while reading through the existing implementation. God knows how much longer it would have gone unnoticed if we hadn't needed to reuse that logic.

Thankfully, it wasn't causing incorrect billing calculations in production. But it was still a problem. It had introduced unnecessary complexity and made the existing implementation harder to understand, maintain, and extend.

What I found interesting about this bug wasn't just the incorrect calculation. It was how two incorrect implementations managed to produce an apparently correct result.

**Sometimes, the most dangerous bugs aren't the ones that break your application. They're the ones that make you believe everything is working fine.**

— _Nikhil Gautam_
